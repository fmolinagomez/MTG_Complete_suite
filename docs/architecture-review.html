Problem:

The GUI module leaks 600 lines of execution logic, multi-deck downloading loops, separator card PIL drawing, and token manifest compilation into Tkinter worker threads.

Solution:

Collapse multi-deck compilation, separator drawing, and token reports into a deep Print Job Engine module behind a unified execution interface.

Architectural Wins:

  • locality: execution concentrates in core engine
  • deletion test: deletes 600 LOC from UI
  • leverage: one interface powers GUI, CLI, and proxies
  • testability: headless tests verify separator cards
  • interface shrinks: caller passes one PrintJobSpec
  • seam: unified progress and cancellation event stream

Problem:

External deck downloading, thread pools, card expansion, and fallback back generation are duplicated across four shallow scraper modules.

Solution:

Unify external deck downloading and slot expansion behind a deep Deck Intake module with game-specific parser adapters.

Architectural Wins:

  • locality: downloading logic concentrates in one module
  • leverage: one interface across four game engines
  • seam: four adapters justify the intake seam
  • deletion test: deletes 4 redundant downloading loops
  • interface shrinks: absorbs thread pools and retries
  • testability: tests mock one canonical intake interface

Top Recommendation

1. Collapse GUI Execution Monolith into a Deep Print Job Engine

The GeneratorView._work monolith (600+ lines) is currently the highest-friction hotspot in the codebase. Extracting multi-deck coordination, separator card generation, and token manifest generation into a deep Print Job Engine concentrates all core business logic into a headlessly testable module, drastically simplifies the GUI, and establishes the unified execution interface needed by the missing proxy generator in InventoryView.
